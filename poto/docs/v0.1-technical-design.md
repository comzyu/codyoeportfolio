## 1. Image processing pipeline

### 1.1 Mental model

Three stages, always in this order. It mirrors a real camera, which makes every later decision obvious:

```
LENS  →  FILM  →  PRINT
(moves/adds light)   (the look: LUT)   (grain, date stamp)
```

- **Lens**: geometry (orient, un-mirror, crop to 3:4, scale), double-exposure blend, lens effects, the flash hot-spot. Everything "in front of the film".
- **Film**: the look's 3D LUT. One lookup. Nothing else.
- **Print**: vignette, light leak, grain, date stamp. Everything "on the paper".

### 1.2 Capture → saved JPEG

| # | Step | API | Thread | Target (mid-range Android) |
|---|---|---|---|---|
| 0 | Shutter press: haptic, click sound, **exposure committed** (§4.3), developing card starts rising | JS + SQLite sync txn | JS | ≤ 16 ms |
| 1 | `photoOutput.capturePhoto({ flashMode, enableShutterSound: false }, callbacks)` → in-memory `Photo` | VisionCamera | native camera queue | 150–600 ms (device-bound; up to ~1.5 s with flash) |
| 2 | `photo.saveToFileAsync(originalPath)` — the untouched original, EXIF included | VisionCamera | native IO | 50–150 ms, runs **in parallel** with 3 |
| 3 | `photo.toImageAsync()` → `image.resizeAsync(w, h)` → `toRawPixelDataAsync()` | nitro-image | native background | 150–400 ms |
| 4 | `Skia.Image.MakeImage(info, data, rowBytes)` → draw through the film shader into `Surface.MakeOffscreen(1536, 2048, { colorSpace: 'srgb' })` | Skia | worklet runtime (fallback: UI thread, see below) | 30–80 ms |
| 5 | Draw date stamp (if on) on the same canvas | Skia | same | < 5 ms |
| 6 | `surface.makeImageSnapshot()` → `encodeToBytes(ImageFormat.JPEG, 92)` | Skia | same | 40–120 ms |
| 7 | `new File(displayPath).write(bytes)`; same again at 400 px long edge for the thumbnail | expo-file-system | same / JS | 10–40 ms |
| 8 | SQLite: `status = 'developing'`, paths, width/height | expo-sqlite | JS | < 5 ms |

**Total processing budget: ≤ 1.5 s typical, ≤ 3 s worst case.** The reveal needs the image at t ≈ 2 s (§5.1), so there is slack; if processing is late the blank hold stretches rather than the reveal jumping.

**How the UI stays at 60 fps**

- Nothing in steps 1–3 touches the JS or UI thread; they are native async calls.
- Steps 4–7 are the only heavy JS-driven work. Run them inside one worklet on a **dedicated worklet runtime** (`react-native-worklets`), so neither the React thread nor the UI thread blocks. *(U1 — unverified.)*
- **Fallback if U1 fails:** run 4–6 on the UI thread **during the developing card's blank hold** (t = 300–1200 ms after the shutter). The card is a flat, static sheet of paper in that window, so a 100–200 ms hitch is invisible. This is why the reveal has a hold phase at all; do not remove it.
- The developing card never waits for processing. It is driven only by the shutter press.
- Never `await` the pipeline from a render path. The camera screen listens for the photo row to change state.

**Why resize natively (step 3) instead of in Skia.** Decoding a 12 MP photo is 48 MB of RGBA; drawing it into a GPU surface uploads another 48 MB texture. Resizing natively first means Skia only ever sees a 1536×2048 image (12.6 MB). The cost: iOS and Android use different resamplers, so the *input* to the shader differs by a hair between platforms. That is acceptable (the two phones' cameras differ far more) and the parity test (§1.9) feeds the shader a fixed image, so the look itself is still proven identical.

### 1.3 The LUT texture layout (defined once, here)

`generate_looks.py` writes exactly this; the shader reads exactly this.

```
File:      <slug>.lut.png
Size:      1089 × 33 px   (33 slices of 33 × 33, side by side, left → right)
Format:    8-bit RGB, sRGB-encoded values, NO embedded colour profile, no alpha
Addressing for input colour (r, g, b), each an integer 0..32:
    x = b * 33 + r        (blue picks the slice, red runs across the slice)
    y = g                 (green runs DOWN; row 0 is g = 0)
Pixel value at (x, y) = the output colour for input (r/32, g/32, b/32)
Identity LUT check:  pixel (b*33 + r, g) == round(255 * (r/32, g/32, b/32))
```

The `.cube` file is the editable source (Cody round-trips it through Photoshop/Lightroom). `.cube` data order is red-fastest, then green, then blue — the script handles the conversion. `LUT_3D_SIZE` must be 33; the script rejects anything else rather than resampling silently.

### 1.4 The film shader (SkSL)

One `RuntimeEffect`, one pass. The same maths is implemented in numpy in `generate_looks.py` (`render_film`) — that Python is the **reference renderer**; if the two disagree, the shader is wrong.

```glsl
// film.sksl — Poto v0.1. Keep in sync with render_film() in generate_looks.py.
uniform shader src;     // photo after the LENS stage, exactly `size` px, sRGB-encoded
uniform shader lut;     // 1089x33 strip (§1.3). FilterMode.Linear, TileMode.Clamp, no mipmaps
uniform shader grain;   // 512x512 grey tile.  FilterMode.Nearest, TileMode.Repeat
uniform float2 size;        // output size in px, e.g. (1536, 2048)
uniform float  flash;       // 0..1  centre hot-spot, applied BEFORE the LUT
uniform float  vignette;    // 0..1
uniform float  grainAmt;    // 0..1  (0.10 is already strong)
uniform float2 grainOff;    // integer px offset, from the photo seed
uniform float  leakAmt;     // 0..1  (0 = no leak on this photo)
uniform float2 leakPos;     // 0..1  normalised centre of the leak, from the seed
uniform float3 leakColor;   // sRGB-encoded tint

const float N = 33.0;

// Trilinear 3D LUT lookup. The GPU does the bilinear part (r, g) inside one slice;
// we blend the two neighbouring blue slices by hand.
// IMPORTANT: coordinates must be `float` (highp). With `half` (mediump on GLES) x = 1088.5
// loses precision and slices bleed into each other on some Android GPUs.
float3 lut3d(float3 c) {
  float b  = c.b * (N - 1.0);
  float b0 = floor(b);
  float b1 = min(b0 + 1.0, N - 1.0);
  float f  = b - b0;
  // +0.5 = texel centre. r,g land in [0.5, 32.5], so linear filtering never
  // reaches across a slice boundary.
  float2 uv = float2(c.r, c.g) * (N - 1.0) + 0.5;
  float3 lo = lut.eval(float2(b0 * N + uv.x, uv.y)).rgb;
  float3 hi = lut.eval(float2(b1 * N + uv.x, uv.y)).rgb;
  return mix(lo, hi, f);
}

half4 main(float2 xy) {
  float3 c = clamp(src.eval(xy).rgb, 0.0, 1.0);

  // p: 0 at the centre, 1 at the corners (aspect-independent)
  float2 p = (xy - 0.5 * size) / (0.5 * length(size));
  float r2 = dot(p, p);

  // LENS: flash hot-spot. Before the LUT so the look's shoulder rolls it off.
  c = clamp(c * (1.0 + 0.6 * flash * exp(-5.0 * r2)), 0.0, 1.0);

  // FILM
  c = lut3d(c);

  // PRINT: vignette (multiply)
  c *= 1.0 - vignette * smoothstep(0.30, 1.05, sqrt(r2));

  // PRINT: light leak (screen blend of a soft warm blob entering from an edge)
  float2 q = xy / size - leakPos;
  float leak = leakAmt * exp(-dot(q, q) * 7.0);
  c = 1.0 - (1.0 - c) * (1.0 - leakColor * leak);

  // PRINT: grain. Texture, not a hash — sin()-based hashes differ between GPUs.
  // Strongest in the midtones, fades toward pure black and pure white.
  float2 gxy = floor(mod(xy + grainOff, 512.0)) + 0.5;
  float g = grain.eval(gxy).r - 0.5;
  float lum = dot(c, float3(0.299, 0.587, 0.114));
  c += g * grainAmt * 2.0 * (1.0 - 0.7 * abs(2.0 * lum - 1.0));

  return half4(half3(clamp(c, 0.0, 1.0)), 1.0);
}
```

**sRGB vs linear — the decision:** everything is done in **sRGB-encoded** values. The LUT is authored against encoded pixels (that is how `.cube` files from Photoshop/Lightroom work), so encoded in → encoded out is the only correct way to apply it. Consequences:

- The offscreen surface must be created with `colorSpace: 'srgb'`. Skia runs SkSL in the destination's colour space; on a P3 surface the LUT *texture* would be colour-converted before our lookup and the look would shift.
- The LUT and grain PNGs carry no ICC profile, so Skia treats them as sRGB and applies no conversion.
- iPhones capture Display-P3. Skia should convert a tagged image into the sRGB surface on draw *(U5)*. If it doesn't, colours look slightly flat on iOS only — the parity test's P3 input case catches this. Fix: convert in nitro-image before Skia, or request sRGB from the camera.
- Flash, vignette, leak and grain are not physically "correct" in encoded space. They are aesthetic, deterministic and identical on both platforms, which matters more.
- Output JPEGs are sRGB. No P3 output in v0.1.

### 1.5 Effects, in order

| Order | Effect | Stage | Source of values |
|---|---|---|---|
| 1 | Orient, un-mirror, centre-crop to 3:4, resize to 1536×2048 | Lens | `Photo.orientation`, `Photo.isMirrored`, config |
| 2 | Double-exposure blend (if on) | Lens | §1.6 |
| 3 | Lens effect (none shipped in v0.1) | Lens | §2 |
| 4 | Flash hot-spot | Lens | look preset `flash` (only Flashbulb uses it) |
| 5 | **LUT** | Film | look preset `lut` |
| 6 | Vignette | Print | look preset `vignette` |
| 7 | Light leak | Print | look preset `lightLeak { chance, strength, color }` + seed |
| 8 | Grain | Print | look preset `grain` + seed |
| 9 | Date stamp | Print | per-shot toggle (default from look preset `dateStampDefault`) |

**Exposure compensation is not baked.** It is applied by the camera hardware at capture (`exposure` prop / `setExposureBias`), which is better than pushing pixels afterwards. The pipeline has no exposure uniform in v0.1.

**The seed.** Each photo gets `seed`: a random 32-bit unsigned integer generated at shutter press and stored in the photo row. From it, with a tiny integer PRNG (mulberry32, identical in JS and Python):

1. `grainOff = (rand()*512 | 0, rand()*512 | 0)`
2. `hasLeak = rand() < lightLeak.chance`
3. `leakPos` = a point on a random edge: side = `rand()*4 | 0`, position along it = `rand()`
4. `leakAmt = hasLeak ? lightLeak.strength * (0.6 + 0.4*rand()) : 0`

Always draw the four values in this order, even when unused, so re-rendering the same photo is bit-for-bit repeatable.

**Date stamp.** Drawn with Skia text after the shader, on the same surface.

- Text: `'YY MM DD` style → `'26 11 15` (apostrophe, two-digit year, spaces). Local date at capture.
- Font: DSEG7 Classic (licence to verify), size = 3.4 % of image width.
- Position: bottom-right, inset 5 % of width from the right edge and 5 % of width from the bottom.
- Colour: `#FF8A1F`. Glow: the same text drawn first with a blur mask filter, sigma = 0.35 % of width, colour `#FF5A00` at 70 % alpha. Then the crisp text on top at 92 % alpha.
- Never drawn on the original file.

### 1.6 Double exposure

- Costs **1 exposure**, produces **1 photo** (H6 default; confirm in §9).
- Shot A: captured normally; its LENS-stage result (1536×2048, pre-LUT) is written to `tmp/de-<photoId>-a.jpg` at quality 95. Not held in memory. The viewfinder shows a small "1 of 2" marker and a ghost of shot A at 35 % opacity so the second frame can be lined up (this is a framing aid, not a filter).
- Shot B: captured normally. LENS stage blends: `c = 1 - (1 - 0.85*A) * (1 - 0.85*B)` (screen blend, each frame pulled down 15 % so the sum doesn't blow out). Then FILM and PRINT run once on the blend.
- Settings: **flash, exposure bias, zoom and camera side are per shot** (A and B can differ). **Look, date stamp, seed, grain, leak come from the photo** (one set, applied once). `taken_at` = time of shot B. The "original" saved is shot B's file; shot A's original is kept as `original-a.jpg`.
- Cancelling after shot A (tap the marker): shot A becomes a normal single photo. Nothing is lost and the exposure was already spent.

### 1.7 Sizes and memory

| Thing | Pixels | RGBA in memory |
|---|---|---|
| Original (capped, see below) | 4032 × 3024 | 48.8 MB (only while decoding, native side) |
| Display render | 1536 × 2048 | 12.6 MB |
| Thumbnail | 300 × 400 | 0.5 MB |

**Peak estimate per photo (native resize path):** encoded JPEG 4–6 MB + native decode 49 MB + resized 12.6 MB + raw pixel copy 12.6 MB + Skia image 12.6 MB + surface 12.6 MB + snapshot 12.6 MB + encoded output ~1 MB ≈ **115 MB transient**, of which the 49 MB is freed as soon as the resize returns. Steady state between photos: ~0.

Rules to stay out of OOM on a 4–6 GB Android:

1. **Cap the capture resolution at 12 MP** (`targetResolution: { width: 4032, height: 3024 }`). Many Androids offer 48–200 MP modes; a 50 MP decode is 200 MB and will kill the app. "Full resolution" in the plan means "the sensor's normal 12 MP output", not the remosaic mode.
2. **One photo in the pipeline at a time.** A serial queue; a second shutter press while one is processing just queues (the original is already safely on disk).
3. **Release explicitly**: call `dispose()` on the Skia image, surface, snapshot and shaders at the end of each run; drop the nitro `Image` and `Photo` references. Do not rely on GC — JSI host objects look tiny to the JS garbage collector.
4. **LUT and grain textures stay loaded** for the life of the roll (36 KB + 262 KB decoded). Don't reload per photo.
5. Diary grids show **thumbnails only**. The full view loads one display JPEG at a time.
6. If a run fails or the device reports low memory mid-run: release everything, leave the row in `processing`, and retry once after 2 s. Never produce a smaller or upscaled render as a workaround. If the app is killed instead, recovery (§4.4) picks the photo up on the next launch.

### 1.8 Cross-platform sameness

What makes iOS and Android match:

- One renderer (Skia) and one shader, no platform image filters anywhere after the resize.
- Texture-based grain and a texture LUT: no GPU-dependent maths (`sin` hashes, `pow` on mediump).
- Integer seed PRNG instead of `Math.random`.
- Encoding with Skia's bundled JPEG encoder on both platforms.
- Fonts bundled in the app (never system fonts) for the date stamp.

### 1.9 Golden-image test

- **Inputs** (in the repo, made by `generate_looks.py`): `assets/looks/golden/input.png` (768×1024 synthetic chart: ramps, patches, skin tones, two scenes; small so the files stay light — the maths is size-independent). A Display-P3-tagged copy is made on-device by the golden screen.
- **Expected**: `assets/looks/golden/<slug>.expected.png` for each of the 3 looks, rendered by the Python reference renderer with **seed = 20261115**, date stamp off, every effect on.
- **Test (a hidden dev screen, run on one iPhone and one Android):** load input → run the real pipeline from step 4 with the fixed seed → `readPixels` → compare to expected.
- **Pass:** per-channel max abs difference ≤ 3 (of 255) on ≥ 99.9 % of pixels, and mean abs difference ≤ 0.6. Compare raw pixels, not JPEGs.
- Also diff iOS output against Android output directly: same thresholds.
- Date stamp is tested separately (text rasterisation legitimately differs by a pixel): compare with a 2 px tolerance mask around the stamp, or by eye.
- This test is spike S1 and is the **first thing built** in the app.

## 2. Lens system (built, not shipped)

### 2.1 Interface

```ts
type LensId = 'fisheye' | 'prism' | 'starburst' | 'colour-flash' | 'soft-focus' | 'half-frame';

interface LensDef {
  id: LensId;
  name: string;
  /** How many captures make one photo. half-frame = 2, everything else 1. */
  captures: 1 | 2;
  /** SkSL that maps the lens-stage image to a new lens-stage image. */
  sksl: string;
  /** Uniform values for this photo. Must be a pure function of (params, seed, size). */
  uniforms(ctx: { size: [number, number]; seed: number; params: Record<string, number> }): number[];
  /** Tweakable defaults, shown as sliders in the dev menu. */
  params: Record<string, { value: number; min: number; max: number }>;
  /** What the viewfinder draws. Declarative — a lens never touches preview pixels. */
  guide: GuideSpec;
}

type GuideSpec =
  | { kind: 'none' }
  | { kind: 'circle'; radius: number }          // fisheye: the image circle (fraction of width)
  | { kind: 'split'; axis: 'vertical' }         // half-frame: centre divider + "1 / 2"
  | { kind: 'rays'; count: number }             // starburst: small tick marks from centre
  | { kind: 'ring'; inner: number }             // soft focus / prism: sharp centre ring
  | { kind: 'tint-corner'; color: string };     // colour flash: a small colour chip, corner only
```

- A lens is a file in `src/pipeline/lenses/<id>.ts` exporting a `LensDef`, registered in `lenses/index.ts`. Adding a lens = adding one file.
- The six listed lenses each get a **working first-draft shader** in v0.1 so the architecture is proven, but quality tuning is v0.8 work.

### 2.2 Composition with the look

`LENS → FILM → PRINT`. The lens always runs **before** the LUT (the lens is in front of the film), so the look grades the lens's light too, and grain is never distorted by a fisheye. Concretely the pipeline is two shader passes when a lens is active:

1. `lens.sksl` : lens-stage image → intermediate surface (same size)
2. `film.sksl` : intermediate → final

With no lens, pass 1 is skipped. Passes are not merged into one shader: keeping lenses separate is what makes them droppable later as remote items.

Half-frame reuses the double-exposure plumbing (two captures, one photo, shot A parked in `tmp/`), but places A and B side by side instead of blending.

### 2.3 Framing-guide contract

- One component: `<LensGuide spec={lens.guide} />`, absolutely positioned over the viewfinder, `pointerEvents="none"`.
- Drawn with hairlines in `paper` at 60 % opacity. No fills over the image, no blur, no colour shift: **the viewfinder stays plain** (product decision).
- Guides must be legible on both bright and dark scenes (1 px light line with a 1 px dark shadow line).

### 2.4 Hidden dev menu

- Photo rows already carry `lens_id` (nullable) so nothing changes in the schema when lenses ship.
- Config flag `lensTestMenu` (default `false`; `true` in development builds via `app.config` extra).
- When the flag is on: **7 taps on the look name within 3 s** on the camera screen opens `/dev/lenses` — pick a lens, tweak its params, and it stays active for subsequent shots until cleared. A small "LENS: FISHEYE" mark shows in the viewfinder corner so test shots are never confused with real ones.
- When the flag is off, the route is not registered and the tap handler is not attached.

## 3. Camera layer

### 3.1 What VisionCamera v5 gives us (verified from source)

```tsx
const photoOutput = usePhotoOutput({
  targetResolution: { width: 4032, height: 3024 },
  containerFormat: 'jpeg',
  quality: 0.95,
  qualityPrioritization: 'balanced',
});

<Camera
  style={viewfinder}            // a 3:4 box
  resizeMode="cover"
  device={device}               // a CameraDevice, or just 'back' / 'front'
  outputs={[photoOutput]}
  isActive={isFocused && appActive && !developing}
  zoom={zoomSV}                 // number | SharedValue
  exposure={exposureSV}         // number | SharedValue, in EV
  mirrorMode="auto"
  orientationSource="interface"
  enableNativeTapToFocusGesture
/>

const photo = await photoOutput.capturePhoto(
  { flashMode, enableShutterSound: false },
  { onWillCapturePhoto, onDidCapturePhoto },
);
```

- `Photo` (in memory): `width`, `height`, `orientation`, `isMirrored`, `saveToFileAsync(path)`, `toImageAsync()`.
- `CameraDevice`: `position`, `isVirtualDevice`, `physicalDevices`, `zoomLensSwitchFactors`, `minZoom`, `maxZoom`, `hasFlash`, `hasTorch`, `supportsExposureBias`, `minExposureBias`, `maxExposureBias`.
- `CameraController` (via ref): `zoom`, `displayableZoomFactor`, `setZoom`, `startZoomAnimation`, `setExposureBias`, `setTorchMode`.
- `photoOutput.prepareSettings([...])` pre-warms capture settings — call it for the current flash mode whenever it changes, to cut capture latency.
- No frame processors, no `previewImageTargetSize` (we never show a preview of the shot).

### 3.2 Pitfalls and fallbacks

| Area | Pitfall | What we do | Fallback |
|---|---|---|---|
| **Device selection** | Passing `'back'` lets the library pick; on multi-lens phones that may be a single wide lens, so 0.5× is impossible. | Enumerate devices; prefer the back **virtual** device (`isVirtualDevice`, type `triple` > `dual-wide` > `dual`) so the OS handles lens switching. | If no virtual device: use the wide-angle device and, if a separate ultra-wide physical device exists, **switch `device`** when 0.5× is tapped (viewfinder blinks ~300 ms; hide it with the same curtain animation as the shutter). |
| **Zoom steps 0.5× / 1× / 2×** | On a virtual device the zoom *value* is not the number printed on the button; `zoom = 1` can mean the ultra-wide. The convention is under-documented *(U3)*. | At session start compute `k = controller.zoom / controller.displayableZoomFactor`. A UI step `s` maps to device zoom `s * k`. Show a step **only if** `minZoom ≤ s*k ≤ maxZoom`. 2× is digital crop where there's no tele lens — fine. | If `displayableZoomFactor` is unreliable on a device: fall back to `zoomLensSwitchFactors[0]` as the 1× point; if that's empty, the device has one lens → show 1× and 2× only. |
| **Zoom while shooting** | Pinch zoom would give "in-between" values that can't be reproduced. | No pinch. Three fixed steps only. `enableNativeZoomGesture` stays off (it also throws if `zoom` is set). | — |
| **Flash vs torch** | `flashMode: 'on'` throws if `!device.hasFlash`. Ultra-wide and front cameras often have no flash. Android flash metering is slow and inconsistent. | Check `hasFlash` every time the device changes; hide Auto/On when false. Use real `flashMode` for the back camera. | Android devices where flash photos come out dark (pre-flash metering bug): config flag `androidTorchFlash` → `setTorchMode('on')`, wait 250 ms, capture with flash off, torch off. |
| **Front flash** | No hardware flash. | Screen flash: full-screen `#FFF8EE` overlay from 150 ms before capture until `onDidCapturePhoto`. | Brightness boost needs `expo-brightness` (not in the dependency list — listed under Suggestions). |
| **Front mirroring** | Preview is mirrored (expected). The saved photo must be **unmirrored** (H6 default). `mirrorMode` applies to outputs; behaviour of `toImageAsync` with `isMirrored` is *U2*. | Keep `mirrorMode="auto"`; the LENS stage reads `photo.isMirrored` and flips to whatever config `frontCameraMirrored` (default `false`) asks for. | **Orientation** | EXIF orientation is "lazy"; decoders disagree about honouring it. Landscape-held phones produce landscape photos, but the postcard is 3:4 portrait. | Lock the app to portrait and use `orientationSource="interface"`: **what you framed is what you get**, always a 3:4 portrait frame. | **Backgrounding** | Camera must stop when the app is backgrounded or another screen covers it. | `isActive` = screen focused AND app active AND no developing card up (saves battery and heat during the 8 s reveal). | — |

### 3.3 Permissions

- Photo library **add-only** permission: asked lazily, the first time someone taps "Save to photos" (v0.1 default: in-app only + manual save). Needs `expo-media-library` — **not in the Section 5 list → ask Cody** (§9, Q7).

## 4. Local data model and offline robustness

### 4.1 SQLite schema

Shaped like plan §6 so v0.3 sync is a mapping, not a migration. IDs are client-generated UUID v4 strings. Times are ISO-8601 UTC strings. `PRAGMA journal_mode = WAL; PRAGMA foreign_keys = ON; PRAGMA user_version` drives migrations (`src/db/migrations/001_init.ts`, …).

```sql
CREATE TABLE rolls (
  id               TEXT PRIMARY KEY,
  type             TEXT NOT NULL DEFAULT 'personal' CHECK (type IN ('personal','shared')),
  look_id          TEXT NOT NULL,                 -- look slug, e.g. 'sunday'. LOCKED: never updated.
  exposures_total  INTEGER NOT NULL,
  exposures_used   INTEGER NOT NULL DEFAULT 0 CHECK (exposures_used BETWEEN 0 AND exposures_total),
  status           TEXT NOT NULL DEFAULT 'loaded' CHECK (status IN ('loaded','finished')),
  finished_at      TEXT,
  created_at       TEXT NOT NULL,
  updated_at       TEXT NOT NULL
);
-- At most one loaded personal roll.
CREATE UNIQUE INDEX one_loaded_personal_roll ON rolls (type) WHERE status = 'loaded' AND type = 'personal';

CREATE TABLE photos (
  id               TEXT PRIMARY KEY,
  roll_id          TEXT REFERENCES rolls(id),     -- nullable for imports (v0.3)
  frame_no         INTEGER,                       -- 1..27, position on the roll
  source           TEXT NOT NULL DEFAULT 'camera' CHECK (source IN ('camera','import')),
  look_id          TEXT NOT NULL,
  lens_id          TEXT,
  taken_at         TEXT NOT NULL,                 -- UTC
  local_day        TEXT NOT NULL,                 -- 'YYYY-MM-DD' in the phone's zone at capture; the diary key
  status           TEXT NOT NULL CHECK (status IN ('captured','processing','developing','kept','tossed')),
  file_original    TEXT,                          -- relative paths, see 4.2
  file_display     TEXT,
  file_thumb       TEXT,
  width            INTEGER,
  height           INTEGER,
  seed             INTEGER NOT NULL,              -- 32-bit, drives grain/leak (§1.5)
  settings         TEXT NOT NULL DEFAULT '{}',    -- JSON: exposure, flash, zoom, position, date_stamp, double_exposure, timer
  pipeline_version INTEGER NOT NULL DEFAULT 1,    -- bump when film.sksl output changes
  attempts         INTEGER NOT NULL DEFAULT 0,    -- processing attempts, for recovery
  created_at       TEXT NOT NULL,
  updated_at       TEXT NOT NULL,
  UNIQUE (roll_id, frame_no)
);
CREATE INDEX photos_by_day    ON photos (local_day, taken_at) WHERE status = 'kept';
CREATE INDEX photos_unsettled ON photos (status) WHERE status IN ('captured','processing','developing');

CREATE TABLE app_config (
  key        TEXT PRIMARY KEY,
  value      TEXT NOT NULL,                        -- JSON
  updated_at TEXT NOT NULL
);
```

Differences from the server model, on purpose:

- `photos.status` has two extra local-only states, `captured` and `processing`. On sync (v0.3) both map to `developing`; `shared` arrives in v0.4.
- `file_*` columns become `r2_key_*` on the server. `visibility`, `owner_id`, `place_label` etc. are added by the v0.3 migration; nothing here blocks them.
- Tossed photos keep their row (so frame numbers and exposure counts stay true) but lose their files.

### 4.2 Files on disk

```
<Paths.document>/poto/
  poto.db
  photos/<roll_id>/<photo_id>/
      original.jpg        as captured (12 MP cap), EXIF intact — never modified
      original-a.jpg      first frame of a double exposure (only then)
      display.jpg         1536×2048, look applied, quality 92, EXIF stripped
      thumb.jpg           300×400, quality 80
  tmp/                    de-<photoId>-a.jpg, half-written files; wiped of anything >24 h old on launch
```

- Paths in the DB are **relative** to `poto/`. Absolute paths change between app installs/updates on iOS.
- Writes are **atomic**: write `display.jpg.part`, then move to `display.jpg`. A file with its final name is always complete.
- `display.jpg` has no EXIF at all (location never leaks; plan §13).

### 4.3 Exposure counting

One synchronous transaction at shutter press (`db.withTransactionSync`), before the camera is even asked to capture:

```sql
UPDATE rolls
   SET exposures_used = exposures_used + 1, updated_at = :now
 WHERE id = :roll AND status = 'loaded' AND exposures_used < exposures_total;
-- if changes() = 0 → abort: roll is full or not loaded; the shutter does nothing.
INSERT INTO photos (id, roll_id, frame_no, look_id, taken_at, local_day, status, seed, settings, created_at, updated_at)
VALUES (:id, :roll, (SELECT exposures_used FROM rolls WHERE id = :roll), :look, :now, :day, 'captured', :seed, :settings, :now, :now);
```

- It is atomic (one transaction), idempotent against double-taps (the JS shutter handler is also guarded by a `busy` flag that clears when the row is written), and synchronous (≈2–5 ms) so the counter can tick on the same frame.
- **A tossed shot keeps its exposure.** Toss only changes `status`; nothing ever decrements `exposures_used` — with one exception:
- **A capture that never produced a photo is refunded.** If `capturePhoto` rejects (camera error, interruption), the same transaction deletes the row and decrements. Real film doesn't burn a frame when the shutter jams, and charging people for our bugs breaks the no-pressure rule. (§9, Q3.)
- `frame_no` is the exposure number, so a refund can only ever happen to the latest frame; numbering never has holes below it.

### 4.4 Photo state machine and crash recovery

```
            shutter press
                 │  (exposure committed)
                 ▼
            ┌──────────┐  original.jpg written   ┌────────────┐  display+thumb written  ┌────────────┐
            │ captured │ ───────────────────────▶ │ processing │ ───────────────────────▶ │ developing │
            └──────────┘                          └────────────┘                          └────────────┘
                 │ capture failed                       │ fails 3×                          │        │
                 ▼                                      ▼                               Keep│        │Toss
          row deleted, exposure refunded        kept, with the original as display          ▼        ▼
                                                                                         ┌──────┐ ┌────────┐
                                                                                         │ kept │ │ tossed │
                                                                                         └──────┘ └────────┘
```

Each arrow is one DB write that happens **after** the file it depends on is safely in place. So at any instant the row's state tells the truth about the disk.

**On every launch** (`recoverPhotos()`, before the camera mounts), for each row in `photos_unsettled`:

| Found in state | Disk | Action |
|---|---|---|
| `captured` | no `original.jpg` | The app died between press and capture. **Refund**: delete row, decrement `exposures_used`. |
| `captured` | `original.jpg` exists | The file landed but the state write didn't. Move to `processing`, continue below. |
| `processing` | — | `attempts += 1`; re-run the pipeline from the original with the stored `seed` and `settings` (deterministic, so the result is the same photo). After 3 failed attempts: copy a plain resized original to `display.jpg`, mark `kept`, log it. Never lose the photo, never loop forever. |
| `developing` | `display.jpg` exists | The reveal was interrupted (battery died, app killed, phone call). **Mark `kept`** silently — it's in the diary. No replay of the 8 s wait; no forced decision. Matches "leaving without choosing = Keep". |
| `developing` | `display.jpg` missing | Shouldn't happen (atomic writes). Treat as `processing`. |

Other recovery chores on launch: delete `*.part` files; wipe `tmp/` entries older than 24 h (a double exposure whose second shot never came was already saved as a single photo at the time, see below); delete files of `tossed` rows if any remain; if the loaded roll has `exposures_used = exposures_total` and nothing unsettled, finish it.

Double exposure and recovery: when shot A is taken the row is `captured` with `settings.double_exposure = { stage: 'a' }` and A's original saved as `original-a.jpg`. If the app dies before shot B, recovery finds no `original.jpg` but an `original-a.jpg` → renames it to `original.jpg`, clears the flag, and processes it as a normal single photo. Nothing lost.

Backgrounding mid-reveal is not a crash: the reveal clock is wall-clock based (`developing_started_at` held in memory); on return, if 8 s have passed the card shows the finished photo with Keep / Toss.

**Toss:** `status = 'tossed'` immediately, card flies off, a 4 s "Undo" appears (H6 default). Files are deleted when the undo window closes (or on next launch). Undo just sets the status back to `developing`→`kept`.

### 4.5 Roll lifecycle and the locked look

```
(no roll) ──load roll (choose look, confirm)──▶ loaded ──27th exposure settled──▶ finished ──▶ (no roll)
```

- **Load**: insert a roll with `look_id`, `exposures_total = config.roll_size`. The unique index guarantees only one loaded roll.
- **Locked look**: `rolls.look_id` is written once; no code path updates it, and each photo copies it at capture. There is no "change look" UI anywhere — the only way to change is to finish the roll.
- **Finish**: when `exposures_used = exposures_total` **and** the last photo has left `developing` (kept or tossed), set `status = 'finished'`, `finished_at`. The "Roll complete" moment plays, then Load a roll.
- There is no "abandon roll" in v0.1 (listed under Suggestions: "unload roll early").
- App start with no loaded roll → Load a roll screen. With a loaded roll → camera.
- Look presets are read from bundled JSON (`assets/looks/<slug>.json`) through a `LookRegistry`; v0.8 swaps the registry's source for the remote catalog without touching the pipeline.

## 5. Developing, sound and haptics

Exact curves, timings and cue sheets live in `motion-spec.md`. This section is the engineering approach.

### 5.1 Developing card

- The card is an **overlay inside the camera route**, not its own route. A navigation push costs 1–3 frames of JS and can't guarantee < 300 ms; an overlay driven by a shared value can. (The plan's screen list says "developing" — it exists as a component and a state, not a URL.)
- **Movement** (rise, settle, toss fly-off, keep tuck): Reanimated shared values on a plain `Animated.View`. Transforms only.
- **The reveal itself**: a Skia `<Canvas>` inside the card with one RuntimeEffect taking the processed image, a `progress` uniform (0→1) and the grain tile. The shader makes highlights arrive first and colour arrive late (formula in `motion-spec.md` §1). `progress` is a Reanimated shared value → the canvas redraws on the UI thread; React does not re-render during the 8 s.
- **Phases:** blank hold (0 → ~25 % of `develop_seconds`) → develop (→ 100 %) → actions fade in. If the processed image isn't ready when the hold ends, the hold simply continues; the develop phase always gets its full length.
- **Tap during developing** shows "Developing…" for 1.2 s. No skip in v0.1 (config `allow_skip_develop: false`).
- **Reduce motion** (`useReducedMotion()`): no rise animation (card cross-fades in, 150 ms), no grain shimmer, the image cross-fades in over the last 600 ms of the same total wait. The wait itself stays — it is the product, not decoration.
- The camera session is paused (`isActive = false`) while the card is up.

### 5.2 Audio

- At app start (root layout), after fonts: `setAudioModeAsync({ playsInSilentMode: false, interruptionMode: 'mixWithOthers' })`, then create one long-lived player per sound with `createAudioPlayer(require('…/shutter.wav'))` and keep them in a module-level map. Never create a player at the moment of the tap.
- Play = `player.seekTo(0); player.play()`.
- The shutter and advance sounds get **two players each** (round-robin) so a fast second shot doesn't cut the tail of the first.
- Files: 44.1 kHz mono 16-bit WAV (uncompressed → no decoder start-up cost). Sounds are short (≤ 1.2 s), total < 1 MB.
- **Latency risk (U4):** `expo-audio` is a general media player; on Android first-play latency for a short clip can be 50–150 ms. Target: sound within **60 ms** of the press. Spike S4 measures it. If it fails: ask Cody to approve a low-latency sound library (SoundPool/AVAudioEngine-based) — a dependency not in Section 5.
- Our music-friendly choice: `mixWithOthers` — Poto's clicks never pause someone's podcast.

### 5.3 Silent mode

| | iOS | Android |
|---|---|---|
| Hardware state | Ring/Silent switch (or Action button) | No silent switch for *media*; ringer mode is separate from media volume |
| What we do | `playsInSilentMode: false` → the OS mutes our sounds when the switch is on silent. Haptics still fire. | Sounds follow the **media volume** (platform convention: games and cameras behave this way). Haptics follow the system touch-feedback setting. |
| Gap | none | A phone on "vibrate" with media volume up will still click. Reading ringer mode needs a native module — not worth it for v0.1. |
| In-app | Settings toggle **Sounds: on/off** (default on), stored in `app_config`. This is the reliable control on both platforms. | same |

Haptics are never gated by silent mode or by reduce motion (a haptic is not motion). They follow the OS haptic setting only.

### 5.4 Haptics

Mapping in `motion-spec.md`. Engineering notes: call haptics **synchronously in the press handler** before any awaited work; on Android prefer `performAndroidHapticsAsync` variants where the spec names one (they are crisper than the generic impact on most devices), fall back to `impactAsync`.

### 6.3 State management

**No state library.** Three places hold state, each for one kind of thing:

1. **SQLite is the source of truth** for anything that must survive a kill: rolls, photos, config overrides.
2. **One small module store** (`store/appStore.ts`, ~50 lines, `useSyncExternalStore`): the current roll, the photo currently on the developing card, and per-shot camera settings (flash, timer, grid, zoom step, date stamp, double-exposure stage). Written through plain functions that also write SQLite when needed. This is all the "global" state v0.1 has.
3. **Reanimated shared values** for anything that changes per frame (reveal progress, card position, exposure slider).

Why not Zustand/Redux: it isn't in the Section 5 list (rule 3), and v0.1 has roughly ten global fields. If v0.3 sync makes this painful, revisit then.

Screens that list data (diary) query SQLite on focus and after the store emits a `photosChanged` event. No ORM, no query cache.

## 9. Open questions for Cody

Each has a recommended answer; the build proceeds on the recommendation unless Cody says otherwise.

| # | Question | Recommendation |
|---|---|---|
| Q1 | **"Full resolution" cap.** Cap originals at 12 MP (4032×3024) even on 48–200 MP phones? | **Yes.** Bigger files add nothing a film look won't hide and are the main crash risk on Android. |
| Q2 | **Orientation.** If someone holds the phone sideways, do they get a landscape photo, or always the 3:4 portrait frame they see? | **Always the 3:4 portrait frame.** Simplest, matches the postcard, "what you framed is what you get". Landscape can come with the extra aspect ratios later. |
| Q3 | **Camera failure.** If the phone fails to capture (error, interrupted), is the exposure refunded? | **Refund.** Tossed shots still cost an exposure; our bugs shouldn't. |
